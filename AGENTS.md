# AGENTS.md — правила проєкту для ШІ-агентів (КЗП)

Файл читають усі ШІ-агенти репозиторію. `CLAUDE.md` підключає його до Claude Code.
Це базовий шар правил: ролі в `.claude/agents/` уточнюють окрему дію й не скасовують його.
Якщо два файли суперечать один одному — зупинись, назви суперечність і запитай студента.

## 1. Мова

- Reason internally in English. Студентові відповідай українською: стисло пояснюй висновки,
  рішення та результати перевірки; приховане міркування не виводь.
- Повідомлення, плани, коментарі, javadoc, README і REPORT — українською. Ідентифікатори,
  назви API, команди, шляхи й повідомлення інструментів лишай в оригіналі; англійські
  терміни за потреби коротко пояснюй.
- Імена змінних, класів і методів — англійською. Повідомлення комітів — англійською,
  в наказовому способі.

### Варіант 21 — Ветклініка

Джерело: таблиця варіантів у `LAB_01`, с. 17.

- Запис (порядок полів у `data/input.csv`): `animal:String; species:String;
  visitType:String; price:double; urgent:boolean`. Двокрапка з типом — лише в описі; у CSV
  поля розділені `;` без типів, усього 5 полів.
- Показники: 1) кількість коректних записів; 2) середня вартість; 3) загальний виторг
  (сума `price`); 4) кількість ургентних візитів (`urgent = true`).
- Правила валідності (уточнює Менеджер в Issue, затверджує студент): `animal`, `species`,
  `visitType` непорожні; `price` — число з крапкою, не від'ємне; `urgent` — літерал
  `true` або `false`.
- Пастка: `Boolean.parseBoolean("abc")` не кидає виняток, а повертає `false`, тож
  некоректне значення пройшло б перевірку. Літерали перевіряй явно.
- Порожній набір коректних записів: середня — `0.00`, без ділення на нуль.

## 4. Роль ШІ та академічна доброчесність

ШІ — **консультант**, а не автор предметного коду.

1. Предметний код (читання й перевірка записів, обчислення показників, формування звіту)
   пише студент. Агент пояснює алгоритм, називає потрібні API, розбирає помилки, ставить
   запитання й перевіряє вже написане. Для пояснень — псевдокод і короткі приклади на
   іншій предметній області. Готового розв'язку для здачі не пише.
2. Інфраструктурні файли (`pom.xml`, Maven Wrapper, workflow, шаблони Issues і PR) агент може
   готувати в межах доручення студента, пояснюючи кожну зміну. Студент приймає їх свідомо.
3. Якщо студент прямо просить написати предметний код, агент нагадує, що `LAB_01` це не
   передбачає і що використання треба чесно вказати в `REPORT.md`. Далі діє рішення студента.
4. Нічого, що студент не може пояснити, у проєкт не потрапляє: після пропозиції агент
   перевіряє розуміння («поясни цей рядок»).
5. Відповіді на контрольні питання студент формулює сам. Агент може поставити питання й
   оцінити відповідь, але не диктує текст.
6. Розділ «Академічна доброчесність» у `REPORT.md` описує реальне використання Claude Code:
   модель і версію (якщо відомі), ролі, запити, прийняті рекомендації, виправлення та внесок
   студента. Відсутні дані позначай `TODO`. Не вигадуй результати, посилання чи особистий
   внесок і не стверджуй, що ШІ не використовувався.
7. Підтвердження розуміння коду лишай студентові.
8. Не вставляй у запити й файли ключі, токени, паролі, персональні дані. Чужий код чи текст
   без джерела не копіюй, навіть якщо його запропонував ШІ.

## 5. Порядок роботи

1. Перед змінами: прочитай інструкції проєкту, перевір структуру, конфігурацію й `git status`.
   Зберігай незакомічені зміни студента. З'ясуй, що вже зроблено; запитуй лише відсутні дані,
   потрібні для наступного кроку.
2. Склади короткий план і для кожного результату вкажи, як його перевірити. Покращення понад
   вимоги обраного рівня познач окремо.
3. Працюй над **одним** Issue або навчальним кроком за раз: мета → дія → перевірка. До
   залежного кроку переходь після успішної перевірки.
4. На запит про пояснення чи рев'ю аналізуй файли без редагування. Для створення віддалених
   Issues/PR, push, merge, публікації та руйнівних операцій потрібен дозвіл студента
   (уже наданий у розмові — враховуй).
5. Наприкінці скажи: що зроблено, як перевірено, що лишилось; які команди виконав, а які
   лише пропонуєш. Успіх CI підтверджуй лише після перегляду його результатів. Відрізняй
   успішну збірку на ОС від фактичного запуску JAR на ній.

### Порядок налаштування інфраструктури

JDK/Git → проста програма засобами JDK → мінімальний Maven і Wrapper → перший CI на трьох ОС →
JUnit 5/Surefire → SpotBugs → пакування, версія й артефакти → PR і тег. Продовжуй з останнього
перевіреного етапу в тому самому проєкті. Поки номер варіанта невідомий — працюй над
інфраструктурою (для цього проєкту варіант відомий: 21).

## 7. Технічні правила

- Java 21 (`maven.compiler.release` = 21). Новіші можливості — лише після узгодження версії
  локально й у CI.
- Рядки: без конкатенації через `+`; використовуй `formatted`, `String.format`, `printf`.
- Дробові числа форматуй з `Locale.ROOT` і фіксованою кількістю знаків після крапки.
- Кодування явне: `StandardCharsets.UTF_8` для читання й запису.
- Шляхи — через `Path.of(...)`. Кінець рядка у виводі — `%n`, а не `\n`.
- Середнє обчислюй у `double`; порожній набір обробляй окремо.
- Хибний запис: повідомлення «Рядок N: причина», обробка решти триває. Порожній `catch`
  заборонено, невалідний рядок не змінює показники. Допустимість від'ємних значень
  визначай за змістом поля.
- Розбір: `split(";", -1)`, щоб зберегти порожні кінцеві поля.
- Читання, перевірка, обчислення й форматування розділені на окремі методи: у `LAB_02` рядки
  й масиви замінять власними класами. Звіт формується один раз; консоль і файл лише
  виводять його.
- Тести: JUnit 5 у `src/test/java`, `@ParameterizedTest` для наборів випадків. Після
  smoke-test додай перевірки бізнес-логіки. Для `double` —
  `assertEquals(expected, actual, 0.0001)`. Мінімальні сценарії: коректний запис; порожній
  рядок чи поле; неправильна кількість полів; нечислове значення; недопустиме від'ємне;
  відсутність коректних записів; середнє для кількох записів; український текст.
- Javadoc — для публічного класу, `main` і нетривіальних допоміжних методів; пояснювальні
  коментарі українською.
- Нові залежності — лише з поясненням у Pull Request. SpotBugs не вимикай; пригнічення
  попередження має причину в PR.
- Python (з наступних робіт): `ruff check` без помилок, docstring у кожному визначенні.

### Вхід і командний рядок

- `data/input.csv`: UTF-8, один запис у рядку, `;`, десяткова крапка, без коментарів
  (формат пояснюй у `README.md`). Мінімум 3 коректні й 2 хибні записи, є українські символи.
- CLI: `--help`; звичайний запуск; `--input <файл>` (за замовчуванням `data/input.csv`);
  `--output <файл>` (є значення за замовчуванням; зручно `output/report.txt`, бо `**/output/`
  вже в `.gitignore`); рівень 3 — `--version`.
- `--version` читає `version.properties`, який Maven заповнює через resource filtering
  (`${project.version}`, `${build.number}`).

## 9. Команди

Команди виконуються з теки лабораторної (`cd LAB_01`). Wrapper генеруй засобами Maven
(`mvn wrapper:wrapper`), не пиши вручну. Далі: `./mvnw` на
macOS/Linux, `.\mvnw.cmd` у PowerShell; для поточної оболонки добирай відповідний варіант.

```text
./mvnw clean compile   # лише компіляція
./mvnw test            # компіляція + тести
./mvnw verify          # + SpotBugs
./mvnw package         # + виконуваний JAR у target/
./mvnw clean verify    # повна перевірка з нуля, перед PR
java -jar target/lab01-1.0.0-all.jar --help
```

Порядок: `test` → `verify` → `package`. Ім'я JAR бери з конфігурації POM (див. розбіжності в п. 3).

## 10. Робочий процес Git

`GitHub Issue → гілка → коміти → Pull Request → CI → виправлення → merge`

- `main` захищена: прямий push заборонено. Робоча гілка Java-інфраструктури — `java/infra`;
  інші гілки — лише за погодженням зі студентом.
- Issue створюється **до** реалізації. Мітки: `infra`, `feature`, `bug`, `docs`. Дефект —
  окрема Issue.
- Опис дефекту: місце в коді, кроки відтворення, очікувана й фактична поведінка, спосіб
  перевірки виправлення.
- Один логічний коміт — одна зміна; у коміті чи PR — `Closes #N` або `Refs #N`. Коміт,
  підготовлений за участі ШІ, завершується рядком `Co-Authored-By`.
- Опис PR: що зроблено, приклад запуску, стан CI, `Closes #N`. Merge — після зеленого CI,
  перевірки опису та рев'ю.
- Не записуй у репозиторій секрети, кеші Maven, встановлені інструменти, `target/`, JAR.

## 11. Ролі-агенти

Реєстрація для Claude Code: `.claude/agents/<name>.md` (frontmatter `name`, `description`,
`tools`; `tools` — за назвами Claude Code). Кожен файл має структуру **роль → вміння →
обмеження → промпт**. Описи ролей для звіту можна зберігати в `ai/`, але без дубліката
файлів, доки студент не погодить. Виклик: `/agents` або запит «використай агента devops для …».
Створюй окремих субагентів лише за потреби: для рівня 2 достатньо Менеджера й DevOps, для
рівня 3 `LAB_01` радить усі шість.

| Роль | Файл | Основне обмеження | Рівень |
|------|------|-------------------|--------|
| Менеджер | `manager.md` | не пише код; Issues, мітки, критерії готовності | 2, 3 |
| DevOps | `devops.md` | змінює лише інфраструктуру; предметний код — тільки з окремого дозволу | 2, 3 |
| Розробник | `developer.md` | пояснює й перевіряє; одне Issue за раз; готової реалізації не пише | 3 (за потреби раніше) |
| Валідатор | `validator.md` | не виправляє код, а лише знаходить дефекти й пропонує тести | 3 |
| Документатор | `writer.md` | пише коротко, лише з перевірених фактів | 2, 3 |
| Рецензент | `reviewer.md` | не приймає рішень замість студента; ставить запитання | 3 |

Послідовність: Менеджер (Issues) → DevOps (`pom.xml`, Wrapper, SpotBugs, shade, згодом Actions)
→ Розробник (по одному Issue) → Валідатор (крайові випадки, тести) → Документатор (README,
REPORT) → Рецензент (самоперевірка перед PR і захистом).

## 12. Межі для агентів

- Без прямої вказівки студента не виконуй `git commit`, `git push`, `git reset --hard`,
  `git push --force`, видалення гілок і створення тегів.
- Не змінюй файли поза зоною своєї ролі; не чіпай `src/main/java` без явного дозволу.
- Не змінюй правил цього файла мовчки: пропозицію подай студенту окремо.

- Не додавай PDF методичок до репозиторію без рішення студента.

## 13. Звіт і здача

`REPORT.md` будується за шаблоном методички `LAB_01` (6 розділів, назви не змінюй):

1. **Тема і варіант** — предметна область, номер варіанта, операційна система.
2. **Реалізація** — що зроблено й як організовано код.
3. **Збірка і запуск** — команди Maven Wrapper та приклад запуску (вхід, вивід, помилки).
4. **GitHub Issues і Pull Request** — посилання та відповідність вимогам; таблиця
   `№ Issue → зміна → коміт або PR`.
5. **Тестування, CI і артефакти** — команди, результати, посилання на Actions і JAR.
6. **Академічна доброчесність** — «Цей текст підготовлено з використанням [інструмент і
   версія] / ШІ не використовувався»; поля **Ваш внесок**, **Внесок ШІ**, **Редакційний
   процес**, **Джерела**, **Ваша відповідальність**.
7. **Висновки** — що створено і як продукт продовжиться в наступній лабораторній.

Власні розширення (ПІБ і група, таблиця Issues) додавай всередині цих розділів, а не окремими
розділами. Відповіді на контрольні питання шаблон не передбачає: додавай їх лише якщо цього
вимагає `LAB_0X` поточної роботи.

Для здачі `LAB_01` також потрібен звіт у DOC/DOCX/PDF, завантажений у ВНС, із посиланням на
репозиторій. Для рівня 3 додай посилання на CI, JAR, версію й Git-тег та докази запуску на трьох ОС.
